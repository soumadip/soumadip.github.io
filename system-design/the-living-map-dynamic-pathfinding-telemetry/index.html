The Living Map (Dynamic Pathfinding & Telemetry)

Target Scale
10M Concurrent Navigations, 2M Telemetry Pings/Sec
Availability
99.99% (High Availability)
Core Tech: Graphs Kafka Geohash A* Search Contraction Hierarchies

1. Problem Statement & Scope

Building a static mapping application is a solved computer science problem. You load a graph into memory and run A* Search. However, building a living map—one that ingests continuous telemetry from millions of moving vehicles to dynamically adjust edge weights and recalculate active routes in real-time—is a monumental exercise in stream processing, parallel computing, and advanced graph theory.

Functional Requirements

  • Spatial Resolution: Map raw GPS coordinates (latitude/longitude) to the nearest logical road segment.
  • Dynamic Pathfinding: Calculate the optimal route between two points based on current traffic conditions, not just static speed limits.
  • Active Re-routing: Continuously monitor active trips and proactively push new routes to clients if a faster path emerges due to sudden congestion.

Non-Functional Requirements

  • Massive Write Ingestion: The system must swallow millions of GPS telemetry pings per second without bottlenecking.
  • Sub-Second Latency: Route calculation must complete in $< 100$ms, even for cross-country queries.
  • Eventual Consistency for Traffic: A sudden highway closure should reflect in the routing engine’s weights within seconds.

2. Back-of-the-Envelope Estimation

  • Active Users: 10 million concurrent drivers actively navigating.
  • Telemetry Ingestion: Each client pings their GPS location every 5 seconds.
    • $10,000,000 / 5 = 2,000,000$ write QPS.
  • Routing Requests: Most users just drive; they only request a full route calculation at the start of a trip or upon missing a turn. Assume 20,000 QPS for pathfinding.
  • Graph Size in RAM: The entire road network of a large country (e.g., India or the US) contains tens of millions of nodes (intersections) and edges (road segments). Storing this graph with basic metadata (speed limits, segment IDs) requires roughly 20GB to 50GB of RAM. This easily fits into the memory of a single modern server, meaning the graph can be highly replicated rather than sharded.

3. High-Level Design (HLD)

To handle the dichotomy between massive write-heavy telemetry and read-heavy graph traversal, we completely decouple the ingestion pipeline from the routing engine using a stream processing architecture.

4. Deep Dive: Component Design

Spatial Indexing: Snapping to the Grid

When a user requests a route, they provide raw GPS coordinates. The routing algorithm only understands graph nodes. How do we quickly find the nearest intersection?

We divide the earth into a grid using Geohashes or a QuadTree. A Geohash converts a 2D coordinate into a 1D alphanumeric string (e.g., tdr1v). The longer the string, the smaller the bounding box. By querying a spatial database for the user’s Geohash prefix, we reduce the search space from millions of nodes down to a few dozen in the immediate vicinity, allowing a rapid linear scan to “snap” the user to the nearest road segment.

The Routing Algorithm: Beyond Dijkstra

If you run standard Dijkstra or even A* Search on a continental graph with 50 million nodes, calculating a route from Mumbai to Delhi will take several seconds—unacceptable for a real-time API.

Instead, modern mapping engines utilize Contraction Hierarchies (CH) or Customizable Route Planning (CRP).

  • Contraction Hierarchies: This algorithm pre-processes the graph by identifying “unimportant” nodes (like a dead-end street) and bypassing them with “shortcut” edges. During the actual query, the search rapidly jumps onto major highways (shortcuts), ignoring local roads entirely unless they are near the origin or destination. This reduces search time from $O(V \log V)$ to practically $O(1)$.
  • Customizable Route Planning (CRP): The flaw with CH is that if a traffic jam changes the weight of a single road, the entire pre-calculated hierarchy is invalidated. CRP separates the topology (the physical connections) from the metric (the travel time). It pre-calculates the topology offline, allowing the metric weights to be updated in real-time by the telemetry pipeline without triggering a massive recalculation of the graph structure.

The Telemetry Pipeline: Edge Aggregation

Ingesting 2 million GPS pings per second directly into a central database is architectural suicide. Furthermore, in dense LTE networks, aggressive handover management and load balancing between edge cell towers can cause out-of-order packet delivery or jitter in the telemetry stream.

We push the first layer of processing to the network edge. The API gateways batch the incoming GPS pings and publish them to Apache Kafka.

A stream processor like Apache Flink consumes this topic, applying a Sliding Time Window (e.g., aggregating all speeds on Segment ID 12345 over the last 60 seconds). Flink calculates the moving average speed and compares it to the static speed limit. If the speed drops by 20%, Flink publishes a new “Congestion Multiplier” for that specific edge into a high-speed key-value store (like Redis), which the Routing Services constantly poll.

Question to ponder: A vehicle is stuck at a red light. Its GPS ping says it is traveling at 0 km/h. How does your stream processor differentiate between a normal traffic signal, a user who just parked their car, and a massive multi-car pileup? If you naively average the zeros, you will flag every intersection in the city as a traffic jam.

5. Fault Tolerance & Edge Cases

The Thundering Herd of Re-routes

A major arterial bridge is suddenly closed due to an accident. The Flink pipeline detects zero throughput and updates the edge weight to $\infty$.

The Routing Service realizes that 50,000 active navigators are currently routed over that bridge. If the system immediately sends a push notification to all 50,000 clients triggering a recalculation, the API Gateway will be flattened by an instantaneous Thundering Herd.

The system must introduce Jitter to the re-routing engine. Instead of recalculating everyone simultaneously, the server staggers the push notifications over a 30-second window, prioritizing users who are physically closest to the bridge and delaying users who are still 50 kilometers away.

Braess’s Paradox & The Feedback Loop

If the algorithm detects traffic on Highway A, it re-routes 10,000 cars onto Local Road B. Five minutes later, Local Road B is completely paralyzed by the influx, while Highway A is now empty. The algorithm then routes everyone back to A. The system enters a catastrophic oscillation.

To mitigate this, mapping architectures must abandon deterministic routing for large crowds. Instead of giving 10,000 users the absolute mathematically shortest path, the system employs Probabilistic Routing (or introduces random noise to the edge weights during the calculation). It distributes the load, sending 60% of users to Road B, 20% to Road C, and keeping 20% on Highway A, acting as a macro-level traffic controller rather than just a personal pathfinder.

Question to ponder: If your algorithm intentionally gives a user a slightly slower route (Road C) to optimize the overall traffic flow of the city, are you violating the user’s trust? How do you balance system-wide optimization against individual greedy actors?
